# Live critical path: snapshot, gauge and foam dependencies

Source revision: `5606527dbf15409eb407cbdebd2cf7f05209fdff` (2026-10-03). This is a read-only source audit: the production files were unchanged at inspection and this audit changes only this note. No new optimization, tests, browser run, hardware probe or runtime proof was produced. The ordinary 116,000-cell Padang Big snapshot-field cost of roughly 2.3–2.4 ms is context from earlier live reports, not a measurement made here.

## GPU readback and snapshot passes

| Stage | Current source and work | Ownership / reason it remains |
| --- | --- | --- |
| Upload | `GpuBoussinesq.ts:297–301`: packs H/QX/QZ from solver Float64 arrays into one Float32 upload; 1,392,000 bytes at 116,000 cells. | CPU body/lip coupling can change these inputs. |
| Device readback | `GpuBoussinesq.ts:12,338`: nine copy commands for H, QX, QZ, RATEH, STRENGTH, AGE, NU, PREDX, PREDZ; 4,176,000 staging bytes. | Water/coupling, crest kinematics, breaking and carried solver state use these fields. Export/window/failover contracts also retain them; no field was proved disposable under the present API. |
| Map and unpack | `GpuBoussinesq.ts:355–366`: waits for staging, creates nine subarray **views**, copies into nine owned Float64 solver arrays, then unmaps. Destination writes total 8,352,000 bytes. | Mapped views cannot replace stable solver arrays: unmapping invalidates the mapped backing. `map` includes pending device completion/queue work; it is not a pure transfer-bandwidth timer. CPU encode can overlap GPU execution. |
| Solver bookkeeping | `BoussinesqSolver.ts:395–406`: scans viscosity to retain its peak for the next explicit-viscosity CFL limit. `Breaking.ts:82–85` copies strength and age into the model's separate public arrays. | Removing the scan changes next-step stability. Aliasing the breaking arrays changes the current independent-array contract. |
| Snapshot preparation | `SurfZoneRunner.ts:675` calls the already fused `SurfZoneSimulation.writeUniformFields`, `:1148–1168`. One solver-cell loop fills Float64 velocity X/Z and void-fraction scratch arrays; 2,784,000 destination bytes. | The subsequent interpolation needs velocities/void fractions at the four source cells, rather than interpolated discharge/depth ratios. |
| Snapshot interpolation | `SurfZoneSimulation.ts:1172–1197`: one render-node loop shares mapping, four weights and interpolated depth, then writes surface/foam, flow and aeration directly into the three final Float32 arrays. 101,913 nodes write 2,445,912 bytes. | There is no second surface/flow/aeration packing loop or temporary visual-output clone left to remove. |
| Publication and renderer copy | `SurfZoneWorkerCore.ts:29–34,144–146` transfers 14 existing buffer backings. `SurfZoneHost.ts:166–193` copies the relevant snapshot arrays into renderer-owned arrays. `WorkerSurfZone.ts:171–181` recycles spare snapshot buffers. | Worker publication transfers ownership without whole-array cloning. Renderer arrays must remain valid while the host can transfer/reuse the previous snapshot before the next draw. |

A small exact command simplification was identified: nine readback copies could become five contiguous ranges, `[H,QX,QZ]`, `[RATEH]`, `[STRENGTH,AGE]`, `[NU]`, `[PREDX,PREDZ]`. It removes four encoder calls while preserving every staging byte, map wait and CPU unpack. It was **not selected or implemented**: this does not address the 4 MB readback or the CPU snapshot cost.

The contact-height cache cannot simply supply snapshot heights. `PhysicalSurfWater.nodeHeight` uses nested `sampleCentered` interpolation and returns Float64; the snapshot uses four weighted terms before Float32 output. Operation order and output precision differ. Likewise the existing Float32 rendered bed is not an exact substitute for weighted Float64 solver bed. Any static-bed cache would first need a bed/grid/window/direct-mutation invalidation contract. No new cache is proposed here. For the earlier isolated kernel diagnostic and its live-attribution limits, see [gpu-kernel-probe.md](gpu-kernel-probe.md).

## The gauge runs in ordinary gameplay

`SurfZoneRunner.ts:368` creates `WaveFrameGauge` when a rider exists. Every ridden `afterWater` step calls `measureRide` (`:540,602–614`), regardless of telemetry visibility. Initial status can also obtain a zero-dt frame (`:780`). `waveFrame.ts:44–68,139–141` makes 185 base surface queries over 40 m behind through 52 m ahead of the rider. Steering adds local surface/sample queries (`:231`); a valid face adds five crest-breaking samples (`:202–207`) and up to 161 lateral curl samples (`:213–219`). The gauge's direction and crest-speed history evolve each fixed step.

| Ordinary consumer | Fields / consequence of omitting the gauge |
| --- | --- |
| Pop-up prompt | Runner cue `:595–598`, `takeOffCue.ts:31–39`, rider snapshot `:705` and ride status `:776`; `ridePrompt.ts:19` displays the pop-up window. |
| Default front camera | `PhysicalMode.ts:423–430` derives `follow.crest`; `SpectatorCamera.ts:131–144` uses it to lean toward the incoming crest. This affects ordinary visuals while paddling. |
| Duck-dive coaching | `App.ts:320–323` consumes valid/crestBreaking/aheadOfCrest. |
| Ride analysis and callouts | `rideAnalysis.ts:224–236,288–306` uses face/curl/crest information for pocket/curl time, ride end and maneuver classification; `RideHud.ts:144` displays callouts. `scoreRides=false` only suppresses score calculation (`App.ts:628`). |
| Assisted trim | `SurfZoneRunner.ts:524` passes the previous frame to `withPocketReflex`; `pocketReflex.ts:34–49` can change standing trim. Default `practice` disables this on Big, but `always` remains an ordinary setting (`:54–55`, `main.ts:685–687`). |

`showTelemetry=false` suppresses only the readout UI (`App.ts:299–303,496`; `PhysicalMode.ts:212–219`). It does **not** make the gauge diagnostic-only. Therefore the 185-query base scan cannot be removed while preserving the current cues and default camera. The lateral curl search has narrower consumers: it is unused by the camera/cue/coaching while prone, before ride analysis starts, with reflex disabled. A phase-specific split would still change exposed wave-frame diagnostics and needs an explicit output contract; it is not implemented or proved worthwhile. A lazy-contact design must account for these off-rider probes, since any probe inside a conservative tube envelope can trigger the full contact build.

## Foam cadence is coupled to material air and particles

`FoamField.ts:94–128` updates dense/residual coverage **and** `source`, sorted `sourceCells/sourceCount`, `breakingCells/breakingCount` and `dissipation` every step. After foam (`SurfZoneSimulation.ts:807`), `aerateBores` (`:1124–1135`) feeds breaking cells/dissipation into `AerationField.addBore` and `stir(dt)`, then material aeration advances (`:815`). `PhysicalSurfWater.ts:125–127,183–185` exposes breaking, void fraction and turbulence to bodies: skipping the whole foam update can change buoyancy/wipeouts indirectly. `BubbleCloud.ts:111–125` and `SprayCloud.ts:436–450` consume the source indices/rates and integrate expected spawns as source × dt × cell area.

Dense/residual coverage itself mainly feeds surface shading (`SurfZoneSimulation.ts:1151,1186`), WaveLab Follow's foam threshold (`WaveLab.ts:170`; `crestTracker.ts:14,92`), foam-area reporting and state handover/serialization (`SurfZoneSimulation.ts:681,705–726`). There is no direct solver/contact/front read of these two arrays; front advancement precedes foam (`:799`), and contact builds from height (`SurfZoneRunner.ts:493–496`). This distinction does not authorize skipping the other each-step foam products.

The existing departure stencil is shared at 60 Hz: `FoamField.advect:139–178` records it and `AerationField.ts:132` consumes only the matching solver/time/dt (`AdvectionStencil.ts:44–53`). Naively moving visual foam to 30 Hz with dt=1/30 while aeration stays dt=1/60 prevents sharing and can create **90 departure maps/s** (30 foam + 60 air), versus the current 60 shared maps/s, while only halving dense/residual interpolation. No net saving is assumed. A future visual-only cadence trial would require explicit source accumulation, splash/event timing, wet/dry/window synchronization and handover semantics; it would be an approximation, not an exact replay optimization.
