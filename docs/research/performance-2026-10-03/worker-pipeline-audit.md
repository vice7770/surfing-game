# Worker request pipeline and observational trace

Read-only source audit, 2026-10-03. This audit performed no production changes, candidate implementation, test, browser run or timing. Root later ran the [observational port trace](worker-port-trace.md), which found little time outside the worker pipeline. A third-buffer saving remains **unproven**; the measurement design below is retained separately from those diagnostic results.

## Current pacing and buffer lifetimes

`WorkerSurfZone.ts:60–110,169–181` permits one advance in flight. At ready, buffer A is the main-thread snapshot and an empty B is its spare. Sending B transfers its 14 backing buffers to the worker; A remains readable. The worker fills/transfers B back. On receipt, the host makes B current, converts A to the spare and calls `flush` **inside the same message handler**. If steps are pending, A is immediately transferred for the next job. This does not wait for the next RAF, but the worker cannot start that job before the reply reaches main and the next request reaches worker.

The main renderer uses its own copied arrays (`SurfZoneHost.ts:166–193`), while the host can recycle the older snapshot at receipt. A third set could retain one main snapshot and give a worker one running output plus one queued output. It adds one complete allocation set (at least another 2.446 MB for the three ordinary render-grid fields). It only hides a dependency if a next step was already demanded and can be queued before the running step ends; when no steps are pending, the wait for the next ordinary frame's request is legitimate pacing (`main.ts:670–687`).

**A buffer-only change is unsafe.** `surfZoneWorker.ts:9–14` immediately invokes `core.handle` for each incoming message. `SurfZoneWorkerCore.ts:109–115` starts `advanceAsync` without awaiting a previous advance; `stepping` is bookkeeping for export/restore, not a command queue. Two GPU advances can therefore overlap the shared solver/device/staging state. A separate serial worker command queue is a prerequisite. It must finish step/body work, fill and post each snapshot before beginning the next fixed step, while retaining one publication per step.

## Semantics a bounded queue must preserve or explicitly change

- **Demand and input commitment.** `WorkerSurfZone.ts:122–129` caps six unsent steps and takes the latest held controls while latching pop-up/retry and the most recent placement, including zero-step calls. `:175–180` commits those controls and clears each press only at send. Prefilling a second request commits its held input earlier; input arriving before the old receipt can no longer affect it. That is an additional input-latency policy, not byte-equivalent replay of the present coalescing rule. Runner applies presses once per request/batch (`SurfZoneRunner.ts:506–507`). Queued jobs require per-request step accounting: the existing single `inFlightSteps` cannot simply reset to zero at the first of two replies. Keep a documented total unshown-step bound rather than accidentally raising today's maximum of seven to eight.
- **Reactions and events.** Pending remote reactions are copied into exactly one sent request (`WorkerSurfZone.ts:123,177–181`) and applied before its water step (`SurfZoneRunner.ts:427–458`). Prequeued work can delay subsequently received pushes by another step; it must never replay or discard them. Offline local board reactions remain within serial runner steps. Every `fill` drains lip/stroke events, knock and outgoing reaction (`SurfZoneRunner.ts:706–710`). Main sound and online reaction consumers read only the latest snapshot once per displayed frame (`main.ts:537–583`; `OnlinePlay.ts:58–61`), and `PhysicalMode.ts:711` pushes only that latest pose to the interpolation track. Every-step publication does not guarantee every intermediate payload is consumed if deliveries bunch before RAF. A queue experiment must count skipped sea times/event payloads or add explicit receipt-time accumulation before claiming unchanged event semantics.
- **Export/restore barriers.** Today both wait for the one step underway (`SurfZoneWorkerCore.ts:122–131`); unsent host steps remain after it. A new FIFO must sequence restore and state capture at their message boundary relative to already accepted advances. An export should capture an immutable state before later steps; compression/reply can finish asynchronously from that copy. A restore either drains accepted jobs or explicitly cancels not-started jobs with buffer, press, reaction and outstanding-count reconciliation. Waiting on only the latest promise is insufficient. Look/particle messages (`Core.ts:62–76`) also require an explicit application boundary if queued work exists.
- **Lifecycle.** Before ready, current `flush` cannot send without a spare; settings are retained while spin-up completes. Disposal terminates the worker and blocks future flushes (`WorkerSurfZone.ts:164–170`); a multi-request pool needs ownership/IDs and must not reuse detached or already queued buffers. Current export promises have no disposal-rejection protocol, so do not assume cancellation acknowledgments already exist. No lifecycle fix is implemented here.

## Minimal observational main-thread wrapper

The existing `fps-survey.mjs:118–129` Worker subclass registers an early reply listener before the host assigns `onmessage`. Extend that **QA-only adapter**, using the same main-thread `performance.now` clock:

1. Wrap the original `postMessage` with unchanged `this`, arguments, transfer list, return and exception behavior. For advances, record a per-worker sequence ID, send-start/end, steps and only small input/reaction metadata. Record all other command types for barriers. Do not clone snapshot arrays or alter messages.
2. In the early listener, match each `snapshot` to the oldest unmatched advance (exclude `ready`/`state`). Capture receipt time, sea time and raw `pipelineMs`. Guard ordinary one-flight operation, `steps=1`, `batchSteps=1`, unchanged configuration/quality and immutable served bundle hashes. Carry unmatched sample-boundary requests or exclude them explicitly. Before the host resets its in-flight count, pending can be obtained as `host.outstandingSteps - matchedRequest.steps` on this one-flight path.
3. Timestamp the next actual advance send. Identify whether it came during that same host callback and whether pending was positive at receipt. The implemented QA driver wraps the actual `port.onmessage` callback through the native setter, forwards its original getter/`this`/event/return behavior, and records `handlerStarted`/`handlerFinished` in `try/finally`. The earlier microtask proposal was removed; actual callback boundaries are measured instead. Observer work and transfer costs executed inside that callback remain part of its diagnostic duration.

For matched request i, compute the quantities **before** summarizing distributions:

```text
latency_i = receipt_i - sendStart_i
workerPipeline_i = pipelineMs.total_i       # only with steps=batchSteps=1
nonPipeline_i = latency_i - workerPipeline_i
queuedGap_i = nextSendStart_i - receipt_i    # only when pendingAtReceipt_i > 0
queuedCycle_i = nextSendStart_i - sendStart_i
cycleOutsidePipeline_i = queuedCycle_i - workerPipeline_i
```

`total` is `(batch + snapshot + summary) / batchSteps` (`SurfZoneRunner.ts:793–801`). It covers runner wall time including device-map waiting, fill and status computation; it excludes transport, command dispatch and some wrapper/post overhead. For multi-step jobs use batch + snapshot + summary, not the per-step total. Do not subtract independent quantiles or sum stage quantiles. Retain negative residuals as instrumentation discrepancies rather than silently clipping them.

Report paired medians/tails and the summed outside-pipeline fraction over **backlogged** complete cycles, separately from no-backlog demand waits. Correlate with snapshot intervals, actual draw intervals, sea-time progress, device-map tails and handler/send timing. Short queued receipt→send gaps would rule out a large *host-handler* delay, but would not rule out worker→main→worker transport/task scheduling. A large paired residual would identify time outside the recorded runner pipeline; it would still combine send transfer, worker scheduling, reply transfer, main event-queue delay and omitted bookkeeping. It is not a direct worker-idle measurement. Existing per-stage wall time also cannot distinguish active CPU work from GPU/queue waits.

Keep passive ordinary High/Rich/High-particle/native-quality source guards on frozen 4201 and publish observer overhead/callback/server limitations. No cross-realm clock comparison is needed, but observation perturbs execution and remains diagnostic. Only trace data can establish whether bounded serial queuing has a meaningful available benefit; the third buffer and queue should not be implemented on the strength of source topology alone.
