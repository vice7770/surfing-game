# Foam-only destination pass fusion — source feasibility, 2026-10-04

Verdict: a narrow internal ordinary numeric path is feasible. Leave the existing generic `FoamField.update` unchanged. Compute each destination's exact interpolation and its existing finish arithmetic into the existing private `nextDense`/`nextResidual`, publish the two public arrays only after all cells, then return. Keep the complete Foam → aerateBores → Aeration order. This is a source proposal, not an implemented optimization or a measured saving; no code, tests, build, replay, timing, server, browser, GPU or Git operations were performed for this audit. Five-owner QA preparation remains untouched.

## Present order and the actual saving opportunity

[FoamField.update](/Users/regina/Desktop/Projects/surfing-game/src/wave/FoamField.ts:94) returns immediately for nonpositive dt. Positive dt follows the moving window, completes all advection, publishes both advected fields and commits the stencil; only then does it evaluate the two decay exponentials, reset counts and finish cells in flat ascending order. [advect](/Users/regina/Desktop/Projects/surfing-game/src/wave/FoamField.ts:139) traverses iz then ix, exactly the same ascending cell order as the finish scan, and writes each private destination once. Departure interpolation reads only old public dense/residual; its four weights and left-associated four-term sums must remain unchanged.

The current two public `.set` copies are still necessary if their public array identities are retained. Fusion does NOT remove departures, weights, four source samples per channel, source calculations, native copies, window shifting or the aeration scan. It removes the finish scan's two rereads and two rewrites of public foam, and can reuse the already read local depth instead of reading h again. At116,000 cells this is at most3,712,000 bytes of logical dense/residual read/write traffic plus928,000 bytes of h reads per step; that is source-level accounting, not measured external-memory bandwidth. A wider fused loop may hurt JIT register pressure/branches; no saving is established by this accounting.

Use one internal `updateGrid(dt, breaking: Float64Array, stencil)` entry called only from [Simulation.afterWater](/Users/regina/Desktop/Projects/surfing-game/src/wave/SurfZoneSimulation.ts:807), with a private fused helper inside FoamField. The ordinary input is [whitewaterStrength](/Users/regina/Desktop/Projects/surfing-game/src/wave/SurfZoneSimulation.ts:846): a separately allocated gated Float64Array at628, or Breaking's separately allocated strength at [Breaking.ts65](/Users/regina/Desktop/Projects/surfing-game/src/wave/Breaking.ts:65). It does not alias foam outputs in current constructed simulations. Public generic `update(dt, ArrayLike, stencil?)` stays verbatim and is the whole-update fallback.

For the internal fused positive update:

1. Follow the window exactly once before reading any foam; retain Math.round/copyWithin/fill order and new-column zeroing.
2. Obtain the original two decay factors once, keep their exact expressions and ordering, and begin the same stencil with identical solver/dt metadata. Moving the factors earlier than the old completed advection is safe ONLY in the eligible ordinary no-callback path.
3. Traverse the same iz/ix cells. For a wet cell calculate departure k/tx/tz, four weights and the two original left-associated F64 interpolation sums. Write the same stencil entries. Finish that destination with exactly `previous * keepDense`, residual multiplication plus `LACE_SHARE * (previous - dense)`, strength/bore/dissipation/rate, `dense += rate * dt`, TRACE checks and the same `Math.min` argument ordering. Residual's cap uses this destination's final dense, not old dense or the unbounded temporary. Put final values in private next arrays. Do not overwrite public dense/residual until all destinations have read their old neighbours.
4. Reset counts and write source/index/dissipation in the same ascending-cell order. A dry cell writes +0 to both final fields and source, does not read breaking, does not write a stencil entry, and does not clear old dissipation or index tails. Wet `strength > 0` adds a breaking index even if the measured bore is zero, as now. Only positive rates add a source index. Stale inactive dissipation and full index tails are part of exact public bytes, not garbage to clear.
5. Use the same two public `.set` calls, then commit. All public arrays remain identical objects; only their contents change. Do not swap buffers. End-of-call stencil indices/values/descriptors/ready state are identical, with dry entries left stale as today.

The private next arrays currently end with raw advected values. In this candidate they end with final finished values. They are not public fields, exported state, input to air, or a later source; the next positive advection overwrites every cell. This intentional private scratch-content change must not be confused with public output parity. If a gate requires their old raw end contents too, a single-buffer finish fusion cannot meet it without extra storage/writes that erode the proposed saving. Array identity and next-step behaviour can still be preserved.

## Generic chronology and eligibility

A Float64Array signature alone does not prove safe fusion. The old chronological contract is: full interpolation → dense.set → residual.set → stencil.commit → Math.exp twice → count resets → every ordered breaking getter and finish. After the first breaking getter, all foam is already advected; earlier cells are finished while later cells remain advected. A getter can read/mutate neighbouring public foam, h/q/bed or later strength. Numeric strength that aliases public dense/residual also observes their advected state in the old method; the fused destination reads the prior field instead. Typed subarray aliases have the same problem. Keep these on the untouched generic method.

Math.exp or its property getter can inspect/mutate foam after the old publication. Other replacements matter too: Math.min/max/floor are called during advection, Math.sqrt by boreDissipation during finishing, and Math.round by followWindow. Fusion interleaves finishing Math.min/sqrt calls with future advection Math.min/max/floor calls. Array-instance/prototype `.set` callbacks move from before finish to after it; copyWithin/fill and stencil begin/commit can be instrumented too. Even an exception's partial-public-state timing differs under fusion. Thus ordinary numeric eligibility must mean constructed independent typed arrays, plain numeric decay/solver values, exact owned stencil implementation, unmodified native arithmetic/typed-array methods and no synchronous callback observation during the call. All current worker ordinary objects satisfy the source construction side of that contract, but source inspection is not a runtime-native proof.

Minimal fallback design: keep the internal worker call explicit; before entering its fused loop, compare the relevant Math data descriptors/references with validated module-native references without invoking getters. If exp/min/max/floor/sqrt/round are changed or accessor descriptors, delegate the whole call to generic `update`; never fall back partway through a fused update. Likewise unexpected aliased strength or overridden publication/window/stencil methods must not enter. A small once-per-call descriptor/identity gate is sufficient for supported substitutions; do not grow it into a generic proxy/reentrancy framework. References captured from a function already replaced before import are not automatically native: either validate initial native authority or leave the fused entry disabled in that realm. The generic external default remains eager even for an ordinary typed breaking array, so its callback semantics do not depend on a clever type detector.

Direct typed-array element reads/writes and local JS Number arithmetic have no user getter callbacks on ordinary arrays. Native arithmetic remains double precision; preserve the exact expression tree and avoid Float32 storage, reassociation, weight hoists with different ordering, approximate decay or zero shortcuts. Nonfinite/NaN payload and signed-zero byte behaviour still require differential checks: mathematical equality or NaN-aware assertions are not byte parity. If preserving a raw Float64 store/read boundary proves necessary for NaN payloads, measure that exact guarded variant instead of asserting an untested local-number equivalence.
