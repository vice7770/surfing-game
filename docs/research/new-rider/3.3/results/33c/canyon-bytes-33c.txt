THE FIRST ATTEMPT WAS THROWN AWAY, AND WHY -- A NEW TRAP, WORTH THE NEXT ROUND'S TIME
=====================================================================================================================

The first Canyon B leg of this round printed:

and it printed NO "spun up on the CPU in ... s" line. That is the tell. `scripts/m1-cpu-bench.ts` lines 49-57:

    if (existsSync(statePath)) {
      runner.simulation.importState(decodeSurfZoneState(...readFileSync(statePath)));    // <-- reuse
    } else {

      writeFileSync(statePath, encodeSurfZoneState(runner.simulation.exportState()));
      runner.simulation.importState(decodeSurfZoneState(...readFileSync(statePath)));
      console.log(`spun up on the CPU in ...`);                                          // <-- fresh

`b1.sea` and `c1.sea` were still on disk in this project's scratchpad from step 3.3b's own run (the scratchpad path is
per PROJECT, not per session, and 3.3b's canyon-bytes file names the same directory). So the leg REUSED 3.3b's kept
state instead of spinning up, and the hashes came out different.

**A kept `.sea` does NOT reproduce the reference hashes, even from byte-identical code.** A spun-up run and a run that
cold-imports that same spin-up's exported state are not the same starting point: `exportState()` carries the arrays
the hash covers, but the solver keeps internals it does not export, so the in-memory sea after a build-then-import is
not the sea after an import alone. The reference is a FRESH-SPIN-UP reference and nothing else.

**So: never pass a `--state` path that already exists, and read the "spun up on the CPU" line before the hashes.** The
grid check catches the wrapper trap; this one needs its own check, and a round that skips it can read a clean tree as
a byte-check failure. This round did, for about twenty minutes.
